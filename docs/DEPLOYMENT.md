# Deploying a shared test instance

Two services, deployed separately: a Docker API and a static SPA. The blueprint
at [`render.yaml`](../render.yaml) creates both on Render's free tier.

Read [Before you hand out the link](#before-you-hand-out-the-link) first. It is
about what may be uploaded, not about how to deploy, and it is the part that
does not have a technical fix.

---

## What the free tier costs you

| | Consequence |
|---|---|
| **No persistent disk** | `/app/data` is wiped on every restart and deploy. Uploads, the token vault, the audit chain and the SQLite database do not survive. Testers must download their package in the session that produced it. |
| **Encryption keys are env vars** | These *do* survive, deliberately. A key that changed on restart would make already-uploaded files undecryptable — the failure the persisted dev-key seed exists to prevent. |
| **Sleeps after ~15 min idle** | The next request pays a ~1 minute cold start. The per-minute limiter resets with the process; the daily quota does not. |
| **512 MB RAM** | OCR at 300 DPI is the memory peak. If runs die mid-pipeline, drop `OCR_DPI` to 200 or move to the 2 GB instance. |
| **Free Postgres expires in 30 days** | Not used. The blueprint stays on SQLite, which on an ephemeral disk resets anyway. |

The ephemeral disk is a genuine feature here: nothing accumulates between
sessions, so a test deployment does not slowly become a document repository
nobody is managing.

## 1. Generate the secrets

Three values, generated locally and pasted into Render. None of them ever
enters the repository.

```bash
python -c "from cryptography.fernet import Fernet; print('FILE_ENCRYPTION_KEY =', Fernet.generate_key().decode())"
```
```bash
python -c "from cryptography.fernet import Fernet; print('VAULT_ENCRYPTION_KEY =', Fernet.generate_key().decode())"
```

They must differ from each other — `validate_production_posture` refuses to
start if they match. `SECRET_KEY` is generated by Render itself.

Then decide the accounts. Format is `username:role:password`, comma separated,
roles are `admin | reviewer | preparer | readonly`, passwords need 12+
characters:

```
alice:preparer:correct-horse-battery,bob:preparer:trombone-daylight-9,carol:admin:the-long-one-here
```

Give each colleague their own credential rather than sharing one. The audit log
records who downloaded which client's package, and that is worth nothing if
every download says "tester".

## 2. Deploy

Render dashboard → **New** → **Blueprint** → pick this repository. It reads
`render.yaml` and prompts for every value marked `sync: false`. Fill in the two
Fernet keys, `BOOTSTRAP_USERS`, and `GEMINI_API_KEY` if you want real
extraction rather than deterministic stubs.

Leave `CORS_ORIGINS` and `VITE_API_BASE` blank for now — neither service's URL
exists yet.

The API image takes several minutes to build the first time: PyMuPDF, OpenCV,
spaCy and the `en_core_web_sm` wheel are all large.

## 3. Introduce the two services to each other

Once both exist:

1. On **taxscraper-api**, set `CORS_ORIGINS` to the web service's full origin —
   `https://taxscraper-web.onrender.com`, with the scheme, no trailing slash.
2. On **taxscraper-web**, set `VITE_API_BASE` to the API's origin —
   `https://taxscraper-api.onrender.com` — and redeploy. It is compiled into
   the bundle at build time, so an env change alone does nothing.

`CORS_ORIGINS` is an exact allow-list and must never be `*`. These endpoints
return taxpayer data, and a wildcard would let any site a signed-in colleague
visits read it through their browser session.

## 4. Check the posture before sharing the link

```bash
curl -s https://taxscraper-api.onrender.com/api/settings/health
```

`ocr: true` means Tesseract is installed in the image. `llm: true` means the
Gemini client actually imports and a key is set — it probes the runtime path
rather than reading config, so it does not lie about a missing dependency.

Then confirm the front door is shut:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://taxscraper-api.onrender.com/api/workflows
```

`401` is correct. `200` means `AUTH_DISABLED` is still true, and anyone with the
URL can read every uploaded return. Do not share the link until this is 401.

## How the API keys stay out of reach

**Never in the repository.** Every secret is `sync: false` in `render.yaml`,
which means Render prompts for it once and stores it encrypted. Replacing one
with an inline `value:` would commit it to git history, where deleting it later
does not remove it.

**Never in the browser bundle.** The frontend gets exactly one variable,
`VITE_API_BASE`, and it is a public URL. Everything prefixed `VITE_` is compiled
into JavaScript that anyone can read in devtools — a Gemini key placed there
would be readable by every visitor. The key lives only on the API, and the
browser reaches Gemini only by asking the API to.

**Never in the image.** The Docker build context is `backend/`, so `Files/` (the
real client corpus) and `data/` (raw zone, vault, audit chain) sit outside it
and cannot be copied in even by a mistaken `COPY .`. `backend/.dockerignore`
covers `.env`, the database files and the local venv on top of that.

**Never in logs.** `core/logging.py` installs a redaction filter, audit events
carry token references rather than values, and the bootstrap seeder reports a
malformed `BOOTSTRAP_USERS` entry by position — never by quoting it, which
would print a live password into the host's log retention.

To rotate: change the value in the Render dashboard and restart. Rotating
`SECRET_KEY` invalidates every issued token, which is what you want after
someone leaves the test group. Rotating `VAULT_ENCRYPTION_KEY` makes existing
vault entries unreadable — on an ephemeral disk there are none to lose, but on
a persistent one that is a destructive act.

## The daily quota

Two ceilings on every request, the lower one winning:

| Setting | Default | Bounds |
|---|---|---|
| `DAILY_QUOTA_UPLOAD_PER_CLIENT` | 5 | Document runs, per tester |
| `DAILY_QUOTA_UPLOAD_GLOBAL` | 40 | Document runs, whole deployment |
| `DAILY_QUOTA_CHAT_PER_CLIENT` | 25 | Chat questions, per tester |
| `DAILY_QUOTA_CHAT_GLOBAL` | 200 | Chat questions, whole deployment |
| `DAILY_QUOTA_DEFAULT_*` | 200 / 2000 | Everything else |

The **global** ceilings are the ones that bound the API bill. A per-client cap
multiplied by an unknown number of colleagues is not a bound.

The counters are charged at `POST /workflows/{id}/process` rather than at
upload, because storing a file is cheap and processing it is what spends OCR
CPU and model tokens. They live in the database, so a cold start does not hand
anyone a fresh allowance. Refused requests do not consume budget. Windows are
UTC calendar days, reset at midnight, and `0` means unlimited.

Anyone signed in can see where they stand:

```bash
curl -s -H "Authorization: Bearer $TOKEN" https://taxscraper-api.onrender.com/api/settings/quota
```

Because the counters are in the database and the database is on an ephemeral
disk, **a redeploy resets the day's usage**. If you are guarding a metered key,
redeploy deliberately.

## Before you hand out the link

This application processes real taxpayer information — names, SSNs, addresses,
income. That is the point of the four-zone model and the egress guard, and none
of it changes the following:

- A free-tier host is shared infrastructure with no data processing agreement
  covering taxpayer information.
- Disclosure of taxpayer data by a return preparer is governed by IRC §7216 and
  Circular 230, and by whatever your firm's own policy says about where client
  data may be processed.
- The four-zone model protects client data from *the LLM provider*. It does not
  make an arbitrary host an appropriate place to put a client's return.

**The safe way to run this test:** ask colleagues to upload only synthetic or
already-published documents, and keep the real `Files/` corpus on machines you
control. `Files/` is gitignored and outside the Docker build context, so it will
not deploy on its own — the risk is a colleague uploading a live client
workpaper because nothing stopped them.

If the test genuinely needs real workpapers, that is a conversation with
whoever owns data policy at the firm, and the answer probably involves a paid
host with a signed DPA and a persistent encrypted disk rather than a free tier.
Nothing in this repository can make that decision for you.

## Other hosts

The Dockerfile is not Render-specific and honours `$PORT`.

- **Fly.io** — better fit if you want the data to persist: attach a volume at
  `/app/data` and the vault, audit chain and database survive restarts. Set the
  VM to 1 GB; OCR is tight at 512 MB.
- **Hugging Face Spaces (Docker SDK)** — genuinely free with far more RAM, but
  read its visibility model carefully before pointing it at anything sensitive.
- **Cloudflare Pages / Vercel** — either will serve the frontend faster than
  Render's static hosting. Build `npm ci && npm run build`, publish `dist`, set
  `VITE_API_BASE`, and add an SPA rewrite of `/*` to `/index.html`.

Whatever you choose, keep one instance. The audit log is a hash chain that
concurrent writers corrupt, and both the burst limiter and the daily quota
assume a single process. Scaling out means moving those three things to shared
storage first.
